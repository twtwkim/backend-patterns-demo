# backend-patterns-demo

서버 프로세스가 여러 개일 때 생기는 문제 세 가지를 작게 재현한 예제입니다.
업무에서 겪은 문제를 블로그에 정리하면서, 직접 돌려 볼 수 있게 처음부터 다시 만들었습니다. 회사 코드는 들어 있지 않습니다.

## 실행

Node.js 20 이상이 필요합니다. MongoDB 는 예제가 임시로 띄우므로 따로 설치하지 않아도 됩니다. (처음 실행할 때 MongoDB 실행 파일을 내려받느라 시간이 걸립니다)

```
npm install
npm run once
npm run request-id
npm run publish
```

## 1. 같은 요청이 동시에 와도 한 번만 실행하기

`01-once-only` · 설명: [서버가 여러 개일 때 "딱 한 번만" 실행하기](https://velog.io/@alfog2/%EC%95%84%ED%95%98-12-%EC%84%9C%EB%B2%84%EA%B0%80-%EC%97%AC%EB%9F%AC-%EA%B0%9C%EC%9D%BC-%EB%95%8C-%EB%94%B1-%ED%95%9C-%EB%B2%88%EB%A7%8C-%EC%8B%A4%ED%96%89%ED%95%98%EA%B8%B0-%EC%A1%B0%EA%B1%B4%EB%B6%80-%EA%B0%B1%EC%8B%A0)

프로세스 4개가 같은 토큰으로 저장을 25번씩 동시에 시도합니다. 저장은 한 번만 일어나야 합니다.

```
프로세스 4개 x 25번 = 같은 토큰으로 저장 100번 시도

메모리에 처리 중 표시         저장된 횟수:   4  중복 저장
DB 에서 확인하고 나서 적기     저장된 횟수:  86  중복 저장
조건부 갱신               저장된 횟수:   1  OK
```

- 메모리에 적어 둔 표시는 다른 프로세스가 볼 수 없어서, 프로세스 수만큼 저장됩니다.
- DB 에서 확인한 뒤에 적으면 확인과 적기 사이에 다른 요청이 끼어듭니다. 이 숫자는 실행할 때마다 달라집니다.
- "아직 안 쓴 토큰일 때만 바꿔라" 를 명령 하나로 보내면 성공하는 요청은 하나뿐입니다.

## 2. 요청 하나를 서버 두 대의 로그에서 따라가기

`02-request-id` · 설명: [요청 하나를 서버 두 대에서 끝까지 따라가기](https://velog.io/@alfog2/%EC%95%84%ED%95%98-13-%EC%9A%94%EC%B2%AD-%ED%95%98%EB%82%98%EB%A5%BC-%EC%84%9C%EB%B2%84-%EB%91%90-%EB%8C%80%EC%97%90%EC%84%9C-%EB%81%9D%EA%B9%8C%EC%A7%80-%EB%94%B0%EB%9D%BC%EA%B0%80%EA%B8%B0-%EC%9A%94%EC%B2%AD-ID-%EC%A0%84%ED%8C%8C)

API 서버와 실시간 서버를 따로 띄우고 구매 요청 10개를 동시에 보냅니다. 로그는 서버마다 다른 파일에 섞여 쌓입니다.

```
api.log 중간 부분 (여러 요청이 섞여 있다)
  [api] [83a98fef] 골드 차감 user=user4
  [api] [d0a11bc9] 골드 차감 user=user5
  [api] [7c672101] 골드 차감 user=user6
  [api] [d0928b03] 골드 차감 user=user8
  [api] [440dcbef] 골드 차감 user=user7
  [api] [83a98fef] 가방에 추가 user=user4 item=sword

요청 ID 440dcbef 로 두 파일을 검색
  [api] [440dcbef] 구매 시작 user=user7 item=sword
  [api] [440dcbef] 골드 차감 user=user7
  [api] [440dcbef] 가방에 추가 user=user7 item=sword
  [realtime] [440dcbef] 통보 받음 user=user7
  [realtime] [440dcbef] 화면에 전송 user=user7 "sword 구매 완료"
```

- 요청 ID 는 함수 인자로 넘기지 않습니다. `AsyncLocalStorage` 에 넣어 두고 로그를 남길 때 꺼냅니다. (`context.js`)
- 실시간 서버를 부르는 함수는 `notifyRealtime` 하나이고, 요청 ID 를 싣는 일도 거기서만 합니다. (`api.js`)

## 3. 도중에 죽어도 다시 실행하면 끝나는 출시

`03-resumable-publish` · 설명: [다시 실행해도 안전한 출시 만들기](https://velog.io/@alfog2/%EC%95%84%ED%95%98-11-%EB%AC%B8%EC%84%9C-2800%EA%B1%B4%EC%9D%84-%EA%B0%B1%EC%8B%A0%ED%95%98%EB%8B%A4-%EB%A9%88%EC%B6%94%EB%A9%B4-%EB%8B%A4%EC%8B%9C-%EC%8B%A4%ED%96%89%ED%95%B4%EB%8F%84-%EC%95%88%EC%A0%84%ED%95%9C-%EC%B6%9C%EC%8B%9C-%EB%A7%8C%EB%93%A4%EA%B8%B0)

편집본 문서를 공개본으로 옮기다가 70번째 문서에서 프로세스를 강제로 끝내고, 다시 실행합니다.

```
== 1부: 대비 없는 복사 ==
편집본 문서 120건
출시 (도중에 죽임)
  items: 40건 복사
  문서 70건을 쓴 시점에 프로세스 강제 종료
다시 출시
  items: 40건 복사
  rooms: 60건 복사
  npcs: 20건 복사
  출시 완료
=> 공개본 문서 190건 (120건이어야 함)

== 2부: 다시 실행해도 안전한 출시 ==
...
재출시 (도중에 죽임)
  items: 40건 옮김
  문서 70건을 쓴 시점에 프로세스 강제 종료
  이 시점의 공개본: 120건, 완료 표시: items
바로 재시도
  다른 출시가 진행 중이라 거절됨 (잠금이 아직 유효함)
잠금 유효 시간(3초)이 지난 뒤 재시도
  items: 지난 실행에서 끝남, 건너뜀
  rooms: 65건 옮김
  npcs: 20건 옮김
  출시 완료, 버전 2
=> 공개본 문서 125건 (125건이어야 함)
=> 문서끼리 가리키는 참조 140건 중 끊긴 것 0건
=> 플레이어가 서 있던 ID 6ac70a31d9958f5701d03fa8 의 방: "방 30 (수정됨)"
```

- 잠금에는 유효 시간이 있습니다. 잠금을 쥔 프로세스가 죽어도 시간이 지나면 다음 실행이 가져갑니다.
- 공개본 문서의 ID 는 쓰기 전에 먼저 기록해 둡니다. 다시 실행해도 같은 문서는 같은 ID 로 갑니다.
- 컬렉션 하나를 다 옮기면 완료 표시를 남기고, 다시 실행할 때 건너뜁니다.
- 옮길 때는 "있으면 덮어쓰고 없으면 만든다" 로 써서, 반쯤 옮긴 컬렉션을 처음부터 다시 옮겨도 결과가 같습니다.

## 예제가 다루지 않는 것

- 3번은 옮기는 동안 편집본이 바뀌는 경우를 막지 않습니다.
- 3번의 잠금은 작업이 유효 시간보다 오래 걸리는 경우를 다루지 않습니다. 그때는 잠금을 뺏길 수 있습니다.
- 2번은 통보가 실패했을 때 다시 보내지 않습니다.
